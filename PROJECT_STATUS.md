## Runtime and architecture

- Production runtime: **Cloudflare Pages Functions**. Confirmed live via `/api/health` reporting `runtime: "cloudflare-pages-functions"`.
- Source of truth: GitHub `main`. Merges to `main` auto-deploy via Cloudflare Pages Git integration.
- HTML entry: `functions/_middleware.js` delegates non-asset, non-API requests to `functions/[[path]].js`.
- Page metadata source of truth: `functions/_route-metadata.js`.
- Named route shims (`functions/artists.js`, etc.) are fallback-only while middleware is active.
- D1 bindings: `DEMAND_DB` only. (No `RATE_LIMIT_DB`, no `CLICKS_DB`.)
- Impact bindings: network-level and provider-specific credentials are server-side only. SeatGeek, Vivid Seats, TicketNetwork, Ticket Liquidator, and StubHub International event lanes require runtime configuration and verified destinations; SeatGeek also has artist-level entries. SeatGeek API credentials are used only by controlled discovery/snapshot tooling. **`IMPACT_TICKETMASTER_*` is no longer read by code** and should be removed from Cloudflare. `MOCK_MODE=false` and `ALLOW_MOCK_PRICES=false`; every display lane remains source/exact-event/freshness gated.
- Affiliate model: **Ticketmaster affiliate is gone**—Ticketmaster redirects are plain and unmonetized. All affiliate-provider lanes fail closed when provider configuration, URL/provenance validation, or Impact tracking is unavailable.

## Validation pipeline

Run before committing data, content, or rendering changes:

- `python3 scripts/validate-events.py --for-production` — event schema, hard error on missing `tour_name` key, warning on blank `tour_name` for indexed artists (PR #186).
- `node scripts/validate-guide-routes.mjs` — guide route / content / sitemap drift validation (PR #184).
- `node scripts/validate-artist-provider-claims.mjs` — artist metadata vs `VERIFIED_TICKET_LINKS` drift guard (PR #185).
- `node scripts/validate-cta-provider-state.mjs` (`npm run validate:cta-provider-state`, in `test:mvp`) — read-only CTA ↔ provider-state guard: artist CTAs backed by a verified registry identity, no withheld identity publishing, every publishable event resolvable through `/api/out`, every `machine_high_confidence` row meeting its canonical contract, and every verified provider provenance row carrying a matching redirect-valid provider URL.
- `npm run seatgeek:verify:self-test` — offline invariant tests for the SeatGeek verification script (instant matching, wrong-night rejection, decision matrix, write shape). Run before changing `scripts/verify-seatgeek-events.mjs`.
- `npm run artist:check -- <slug>` — per-artist readiness validator: checks `artists.json`, `catalog.json`, `events.json`, partition files, `VERIFIED_TICKET_LINKS` in `out.js`, and the `shows.js` affiliate map (PR #188; since 2026-06-11 the shows.js map is derived from out.js and the signup allowlist from artists.json — neither is hand-edited per artist).
- `node scripts/smoke-prelaunch.mjs` — route/CTA/copy smoke checks.
- `npm run seatgeek:self-test` — SeatGeek discovery scoring/safety smoke test (no API calls). Run before changing the discovery tooling.
- `npm run providers:identities:validate` — provider identity registry validation (`data/provider-identities.json` vs `artists.json` and the out.js Ticketmaster host allowlist). Run whenever the registry changes. See `docs/PROVIDER_SYNC.md`.
- `node --check public/app.js`, `node --check 'functions/[[path]].js'`, `node --check functions/api/out.js` — syntax.
- `git diff --check` — whitespace and conflict markers.

`npm run test:mvp` runs documentation validation, the events/outbound-link self-tests, provider validators, CTA-provider-state guard, and smoke suite together.

## Daily automation

`.github/workflows/daily-audit.yml` runs at 03:00 UTC and on `workflow_dispatch`. It performs:

1. URL liveness via `scripts/verify-outbound-links.mjs`.
2. Ticketmaster Discovery diff via `scripts/audit-tm-events.mjs` (requires `TICKETMASTER_API_KEY`; skipped safely if absent). The Discovery API is keyed by the **Discovery event id** (`ticketmaster_discovery_event_id` / `provider_links.ticketmaster.discovery_event_id`), NOT the consumer-website `/event/<id>` code stored in `ticketmaster_event_id` (16-char hex) or the international numeric storefront id. Events lacking a Discovery-format id are reported as **`unresolvable`** (surfaced for backfill, **not** counted as missing). `scripts/backfill-discovery-ids.mjs` (`npm run audit:backfill-discovery-ids`, dry-run by default; `--apply` to write) recovers Discovery ids from the verified per-artist attraction feed by venue-local-date + city match, writing only on unambiguous API matches. Date/venue/status comparison is timezone-aware and only flags actionable status transitions (cancelled/postponed/rescheduled).
3. Reporting via `scripts/daily-audit-report.mjs` into a single rolling GitHub issue (`automation:daily-audit`).
4. Verification-date bumps via `scripts/bump-verified-dates.mjs`, opening a PR for human review. The TM-skip/failure guard added in PR #182 prevents date bumps when TM data is unavailable.

`.github/workflows/tm-new-shows-pr.yml` runs at 04:00 UTC and on `workflow_dispatch`. It is the scheduled **new-show discovery loop** (provider-sync step 3, write-to-PR mode): it runs the Ticketmaster Discovery recogniser for every verified, `sync_enabled` artist via `scripts/sync-tm-events-write-pr.mjs`, opens **one PR** (`automation:tm-events` label) of newly-discovered shows, and **auto-merges it (squash) once the in-run validation suite has passed** (owner-approved 2026-07-07; a failed merge leaves the PR open for a human). It never commits to `main` directly. The recogniser withholds events already in `events.json`, so only genuinely new shows are proposed and a quiet day produces no commit and no PR; risky rows are withheld for human review and never auto-merged; `event_name` is populated verbatim from the Discovery API listing title; `tour_name` is left blank for human verification (#172). Manual `workflow_dispatch` defaults to a safe `preview` (no PR), accepts an optional single-artist `artist` input, and only auto-merges when the `auto_merge` input is set. Without `TICKETMASTER_API_KEY` the recogniser no-ops safely (no rows, no PR). See `docs/PROVIDER_SYNC.md`.

`.github/workflows/nightly-data-sync.yml` runs at **03:30 UTC** (cron re-enabled 2026-07-07, owner-approved, after a clean local dry-run: 0 errors, 17 pending lossless updates, 80 review-only items) and on `workflow_dispatch`. Manual runs default to `dry_run: true`; a dry-run writes `.audit/tm-sync.json` as an uploaded artifact and cannot commit or push. A non-dry-run can **auto-commit to `main`** only for lossless factual updates (date/time, venue/city, the official listing title `event_name`, refreshed canonical TM URL) to events that already exist in `events.json`, pulled per event id from the Ticketmaster Discovery API via `scripts/apply-tm-updates.mjs`, then regenerates the inline fallback and partitions. The script only applies updates to events with zero review blockers of their own; the commit is blocked by any error, missing report, dry-run input, validation failure, smoke-test failure, or absent `events.json` diff (review items and blocked updates on other events go to the rolling issue without vetoing the clean updates — the old repo-wide zero-review gate could never pass given the permanently-offsale rows). Items that need human judgement — new shows, deletions (404/410), cancelled/postponed status, `tour_name` — are **never auto-applied**; they are surfaced in the rolling `automation:data-sync` issue via `scripts/report-tm-sync-review.mjs`. See `docs/PROVIDER_SYNC.md` and `SAFE_PUBLISHING_RULES.md` → "Discovery, Enrichment, and Rendering" for the boundary. (`TICKETMASTER_API_KEY` is required for useful live checks; if absent, the run writes a skipped report and no-ops safely.)

`.github/workflows/seatgeek-cta-sync.yml` runs at **05:00 UTC** (added 2026-07-08, owner-approved) and on `workflow_dispatch` (manual runs default to a safe preview). It is the SeatGeek CTA enrichment + verification loop: `scripts/enrich-seatgeek-events.mjs --apply-high-confidence` adds missing event-level `seatgeek_url` values for Ticketmaster-verified events (so newly-discovered shows get SeatGeek CTAs the morning after they land), then `scripts/verify-seatgeek-events.mjs --apply` confirms stored SeatGeek links against the SeatGeek API record for the registry-verified `seatgeek_performer_id` (UTC-instant match ±3h, city and venue match, event-URL shape) and writes `provider_links.seatgeek` verified provenance — which un-suppresses the SeatGeek CTA on `needs_recheck` events. It discovers URLs for suppressed events via a performer-id-scoped ±12h window query, corrects wrong-night URLs to the single unambiguous API match, and un-verifies/clears listings only on positive evidence (confirmed-gone 404/410 or confirmed mismatch, plus a successful zero-candidate discovery query); transient API failures leave events untouched, and auth/config failures (401/403) abort the run with exit 1 and no writes. Ambiguous matches are reported in the committed provider reports (`reports/provider-sync/seatgeek-cta-auto-add.md`, `reports/provider-sync/seatgeek-cta-verify.md`), never guessed. The full validation suite runs in-job before the PR opens; scheduled runs auto-merge (squash) via `scripts/open-automation-pr.mjs` `PR_AUTO_MERGE`, and a failed merge leaves the PR open for a human. Without `SEATGEEK_CLIENT_ID` the run no-ops safely. Only future events are maintained (past shows are skipped — SeatGeek delists them, and this keeps the smoke suite's pinned Gainesville canary untouched); events whose `datetime_iso` is date-only (time TBA) or timezone-naive with no IANA `timezone` field are skipped as date-ambiguous (never guessed).

`.github/workflows/vividseats-cta-sync.yml` runs at **05:30 UTC** (cron enabled 2026-07-12, owner-directed all-shows automation) and on `workflow_dispatch` (manual runs default to a safe preview). Its first reviewed data PR merged 218 verified event destinations; scheduled runs auto-merge after the in-run validation suite, mirroring `seatgeek-cta-sync.yml`. Monitor scheduled runs via the auto-merge PRs and `reports/provider-sync/vividseats-cta-sync.md`.

`.github/workflows/prelaunch-validation.yml` includes a `stale-sync-guard` that runs `npm run events:sync` on PRs touching `public/data/*.json` and fails if `public/index.html` is stale.

## Product guardrails (summary)

The full rules are in `docs/CONTENT_RULES.md`, `docs/PROVIDER_DATA_POLICY.md`, and `CLAUDE.md`. Highlights:

- Never invent tours, dates, venues, prices, availability, providers, inventory, or ticket links.
- Never scrape ticket providers.
- Never claim live price comparison unless approved provider feeds support it.
- Never expose Impact or any other secret client-side.
- CTAs only when the artist/event is reviewed, the provider destination has the required verification/provenance, and the URL, runtime configuration, and `/api/out` gates pass.

## What is not supported

- Live inventory aggregation and "cheapest" / "guaranteed availability" claims. Approved lanes are provider-listed snapshots rather than live checkout totals; each remains fail closed unless its rights, URL, exact-event, source, timestamp, and expiry gates pass.
- Tour, city, venue, or event landing pages.
- Artist-level Vivid Seats CTAs. Event-level Vivid Seats CTAs are supported and live.
- Ticket Liquidator listed-price snapshots while its Impact catalog omits numeric `CurrentPrice`. StubHub US/Canada is not part of the StubHub International integration.
- Ticketmaster affiliate/tracking of any kind (the site is no longer in the Ticketmaster affiliate programme).
