# TourTicketCompare

TourTicketCompare is an independent, unofficial ticket comparison affiliate project. The product goal is to publish trustworthy, SEO-focused artist and tour pages with factual content and verified ticket-provider buttons.

The site must never invent tour dates, venues, prices, ticket availability, or "best deal" claims. External ticket buttons are allowed only when a real destination is verified and routed through the server-side `/api/out` guardrail.

## Current Product Strategy

- Build high-intent SEO pages for artists, tours, and ticket-buying guides.
- Use factual, evergreen artist and tour content rather than fan-blog filler.
- Show provider buttons for Ticketmaster, SeatGeek, and Vivid Seats only when each provider has a verified destination URL.
- Keep prices hidden unless they come from verified provider data with a timestamp and checkout caveat.
- Keep the site clearly independent and unofficial, with affiliate disclosure near outbound flows.

## Tech Stack

- Frontend: static HTML, CSS, and JavaScript in `public/`.
- Cloudflare runtime: Pages Functions in `functions/`.
- Production deployment path: standalone Cloudflare Worker generated by `scripts/build-standalone-worker.mjs` and deployed to Worker `tourticketcompare-live`.
- Vercel preview support: `api/` route handlers and `vercel.json`.
- Storage: Cloudflare D1 binding `DEMAND_DB` for demand capture and first-party analytics.

Keep Cloudflare Pages Functions and the standalone Worker generator aligned. Production currently depends on the Worker route, so changes are not live until the Worker bundle is rebuilt and deployed.

## Current Deployment Topology

Production currently uses Cloudflare Workers, not GitHub Actions or a direct Cloudflare Pages deploy.

- Production custom domains: `tourticketcompare.com/*` and `www.tourticketcompare.com/*`.
- Production Worker: `tourticketcompare-live`.
- Production entrypoint: the generated Worker module from `scripts/build-standalone-worker.mjs`.
- Production build command: `npm run build:worker`.
- Production build output: `/tmp/tourticketcompare-worker.js`.
- Production deploy method: upload the generated Worker module to Cloudflare Worker `tourticketcompare-live` while preserving existing bindings and secrets.
- Cloudflare Pages project: `tourticketcompare`, output directory `public`, build command blank. This is a compatibility/fallback path only while Worker routes own the custom domains.
- GitHub Actions: no workflow is currently configured in this repo.
- Manual Wrangler Pages deploy: available through `npm run deploy:pages`, but it does not update the live custom domain while Worker routes are active.

Beginner rule of thumb: if you want to update `https://tourticketcompare.com`, build and deploy the standalone Worker. Do not assume a Pages deploy changes production.

## Canonical Routes

Use these as the intended canonical route strategy:

- `/`
- `/artists`
- `/artists/[artist-slug]`
- `/artists/[artist-slug]/tickets` redirects to `/artists/[artist-slug]` unless it later has unique, substantial ticket-buying content.
- `/artists/[artist-slug]/[tour-slug]`
- `/guides`
- `/guides/[guide-slug]`
- `/how-it-works`
- `/about`
- `/contact`
- `/editorial-policy`
- `/affiliate-disclosure`
- `/sitemap.xml`
- `/robots.txt`

Root-level artist routes are not canonical. Old routes such as `/beyonce`, `/beyonce-tickets`, and `/beyonce-tickets-london` should redirect to the relevant `/artists/...` route when the artist is known.

Avoid thin duplicate pages. `/artists/[artist-slug]/tickets` should either have unique ticket-buying content or canonicalize/redirect to `/artists/[artist-slug]`.

## SEO And Indexing Rules

- Homepage, artist index, substantial artist pages, guide pages, and trust/legal pages can be indexable.
- Artist pages can be indexable only when they contain substantial factual content.
- Tour pages can be indexable only when tour data is verified.
- City or event pages must not be indexed unless real event date, venue, and availability data is verified.
- Do not add `Event` or `MusicEvent` schema without verified event data.
- Do not index API routes, data JSON, thin duplicate pages, placeholder pages, or unverified city/event routes.
- Sitemap should include only useful indexable pages.
- Every indexable page needs a unique title tag, meta description, canonical URL, H1, useful body copy, internal links, Open Graph tags, and Twitter card tags.

## Artist Content Rules

- Artist content must be factual, evergreen, and useful for someone deciding where to check tickets.
- Do not invent current tour status.
- If tour status is unknown, say: "There may not be an active tour at the moment. Use the verified provider links below to check current availability directly with ticket platforms."
- Use official or publicly verifiable sources for factual claims where possible.
- Store source URLs in the data model or content notes when adding claims.
- Avoid unsupported phrases such as "cheapest", "best price", "sold out", "official tickets", or "best deal" unless verified live data supports them.

## Tour Content Rules

- Create tour pages only when the tour exists in the data model with verified facts.
- A tour page should include tour name, artist, factual overview, verified regions if known, ticket provider buttons when available, buying notes, FAQ, and `last_verified_at`.
- Do not create fake city, venue, date, or event pages.
- Do not publish Event schema until event date, venue, and availability are verified.

## Provider Button Rules

- Provider buttons appear only when the provider has a verified configured destination URL.
- All provider buttons must route through `/api/out`.
- Button labels should be provider-specific, such as `View tickets on Ticketmaster`, `View tickets on SeatGeek`, and `View tickets on Vivid Seats`.
- Hide missing providers instead of showing disabled or placeholder buttons.
- If no provider links exist for an artist, show: `No verified ticket links are available yet. Check back later or follow for updates.`
- Show this disclosure near outbound buttons: `External ticketing sites set their own prices, fees, availability, and checkout terms. Prices may change.`

## Affiliate Redirect Rules

`/api/out` is the only public outbound ticket route.

Required behavior:

- Accept a known artist, optional tour, provider, and source path.
- Resolve the destination from verified server-side configuration.
- Reject `example.com`, localhost, malformed URLs, unknown providers, unknown artists, and arbitrary open redirects.
- Allow provider destinations only for documented provider domains.
- Track outbound clicks in D1 when storage is available.
- Never expose Impact credentials or affiliate secrets to the browser.
- Return clear `400` errors for invalid or missing configuration.

Allowed provider destination domains:

- `ticketmaster.com`
- `ticketmaster.co.uk`
- `seatgeek.com`
- `vividseats.com`

Configured affiliate-network URLs may be used only when they are stored as trusted server-side data and tied to a verified provider link.

## impact.com Publisher Tag

The global HTML head includes the impact.com Publisher Tag once. It calls only:

- `impactStat('transformLinks')`
- `impactStat('trackImpression')`

Do not add `identifyUser` or pass email addresses, account IDs, customer IDs, or other user/customer data to the tag. Keep provider links clean unless a verified server-side affiliate route already exists. Current commercial ticket CTAs continue to route through `/api/out`; do not replace them with manually generated affiliate URLs.

To test link transformation in browser DevTools:

1. Open `https://tourticketcompare.com` and confirm the Network panel loads `https://utt.impactcdn.com/P-A6059518-a226-4662-87f2-2b96ca3deaaa1.js`.
2. In the Console, confirm `typeof window.impactStat === "function"`.
3. Inspect a page with commercial ticket CTAs and confirm the visible disclosure appears: `Affiliate link. We may earn a commission at no extra cost to you.`
4. If a future page contains a direct, clean provider URL, inspect the anchor before and after `impactStat('transformLinks')` runs to confirm any transformation comes from the Publisher Tag, not from hardcoded client-side affiliate URLs.
5. Confirm no `identifyUser` call appears in the page source or Network payloads.

## Deployment

The repository supports Cloudflare Pages, but the live custom domain currently serves Worker `tourticketcompare-live`. Use the Worker flow for production.

### Production Worker Deploy

```bash
npm install
npm run check:worker
```

Then upload `/tmp/tourticketcompare-worker.js` to Cloudflare Worker `tourticketcompare-live`, preserving existing bindings and secrets.

Required Worker settings:

- Worker name: `tourticketcompare-live`
- Compatibility date: `2025-01-01`
- Routes: `tourticketcompare.com/*` and `www.tourticketcompare.com/*`
- `www` behavior: Worker redirects `www.tourticketcompare.com` to apex.

Required Worker bindings:

- `DEMAND_DB` D1 binding to database `tourticketcompare-demand`
- `IMPACT_ACCOUNT_SID` secret
- `IMPACT_AUTH_TOKEN` secret
- `MOCK_MODE=false`
- `ALLOW_MOCK_PRICES=false`
- `CLICK_TRACKING_ENABLED=true`
- `IMPACT_DEFAULT_PROGRAM_ID`
- `IMPACT_TICKETMASTER_PROGRAM_ID`

Optional/legacy provider variables may exist in `.env.example`, but the current production Worker only requires the bindings above for the SEO affiliate build and demand capture.

After deploy, check:

```bash
curl -fsS https://tourticketcompare.com/api/health
curl -fsSI https://www.tourticketcompare.com/
curl -fsS https://tourticketcompare.com/
```

`/api/health` returns configuration and binding presence only. It must never return secret values.

### Cloudflare Pages Compatibility

Cloudflare Pages settings if the route is intentionally moved back to Pages:

- Framework preset: `None`
- Root directory: repository root
- Build command: leave blank
- Build output directory: `public`

Deploy Pages manually only when you intentionally want the Pages preview/fallback:

Do not assume a Pages deploy updates production while Worker route overrides are active.

## How To Add An Artist

1. Add the artist to the structured artist data with factual evergreen copy.
2. Include source URLs for claims when possible.
3. Add SEO title and meta description.
4. Add route metadata and sitemap inclusion only when the page is substantial enough to index.
5. Add provider links only through the verified provider-link workflow.
6. Run smoke tests and check public pages for fake or unsupported claims.

## How To Add A Tour

1. Add a tour record with `artist_slug`, `tour_name`, `tour_status`, factual summary, known regions, source URL, and `last_verified_at`.
2. Use `tour_status: unknown` when status is not verified.
3. Do not add city/date/event pages from a tour record alone.
4. Index the tour page only when the content is substantial and factual.
5. Do not add Event schema unless event-level date and venue data is verified.

## How To Add A Verified Provider Link

1. Confirm the destination URL is real and belongs to an allowed provider domain.
2. Confirm the provider route preserves attribution if an affiliate link is used.
3. Add the link to server-side verified link data.
4. Mark `verified: true`, set `last_checked_at`, and include provider, artist, optional tour, and market/country.
5. Ensure the public UI shows the provider button only through `/api/out`.
6. Run `/api/out` rejection tests and a real redirect test.
7. Confirm credentials and raw tokens are not present in public HTML, JS, CSS, or JSON.

## Do Not Do

- Do not invent artist facts.
- Do not invent tour dates.
- Do not invent ticket availability.
- Do not show fake prices.
- Do not expose affiliate credentials.
- Do not index thin or duplicate pages.
- Do not add provider buttons without verified URLs.
- Do not revive old root-level artist routes as canonicals.
- Do not claim "cheapest", "best price", "best deal", or live comparison unless verified live data supports it.
- Do not create city or event pages without verified event/date/venue data.
