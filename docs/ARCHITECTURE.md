This document describes the repo architecture as confirmed by reading the source. Where something cannot be confirmed without Cloudflare dashboard access, it is explicitly marked as **inferred** or **requires verification**.

## Runtime Overview

| Layer | What it is | Status |
|---|---|---|
| `public/` | Static frontend assets (HTML, CSS, JS, data) | Confirmed |
| `functions/` | Cloudflare Pages Functions (server-side routing + APIs) | Confirmed |
| Standalone Worker | `tourticketcompare-live` — serves production custom domains | Inferred from HANDOVER.md |
| Cloudflare Pages | Preview/fallback URL only while Worker routes own custom domains | Inferred from HANDOVER.md |
| Vercel | Not production; preview path only via `api/` + `vercel.json` | Inferred from HANDOVER.md |

**Important:** The source files in this repo primarily define the Cloudflare Pages path. The production Worker is generated by `scripts/build-standalone-worker.mjs`, which bundles `public/` assets inline and embeds the same routing functions. Changes to `functions/` or `public/` must be propagated to a new Worker build before they affect production traffic.

## Routing Model

### Request flow (Cloudflare Pages)

```
Request
  → _routes.json: routes /* through Functions (excludes /_assets/* and /favicon.ico)
  → _middleware.js
      ├─ API path (/api/*, /data/*)        → context.next() → specific API handler
      ├─ Known static file (/app.js, etc.) → context.next() → served from assets
      ├─ Any file extension (.*)           → context.next() → served from assets
      └─ All other paths                  → [[path]].js onRequest (HTML rendering)
```

### HTML routing logic (all in `[[path]].js`)

| Pattern | Behaviour |
|---|---|
| `/` | Homepage |
| `/artists`, `/guides`, `/how-it-works`, etc. | Static trust pages (title/meta/content injected into `index.html`) |
| `/guides/[known-slug]` | Guide page (rendered with article schema) |
| `/guides/[old-slug]` | 301 redirect to canonical guide slug |
| `/artists/[known-slug]` | Artist page (loaded from catalog.json) |
| `/artists/[known-slug]/tickets` | 301 redirect to `/artists/[slug]` |
| `/artists/[known-slug]/[tour-slug]` | Tour page (only if verified tour record exists) |
| `/[artist-slug]-tickets[-city]` | 301 redirect to `/artists/[slug]` (legacy URLs) |
| `/[artist-slug]` | 301 redirect to `/artists/[slug]` (legacy root-level URLs) |
| Unknown path with no file extension | 404 (noindex; HTML shell injected) |
| Unknown path with file extension | Passed through to assets |

### Named route shims

`functions/artists.js` and similar files each contain exactly:

```js
export { onRequest } from "./[[path]].js";
```

**Behaviour:**
- While `_middleware.js` is in place, middleware intercepts HTML routes and calls `[[path]].js` directly. The named shims are **never invoked** for those routes because middleware returns a full Response without calling `context.next()`.
- If `_middleware.js` is removed, the named shims become the active handlers for their specific routes and will delegate to `[[path]].js` — behaviour is preserved but the routing path changes.
- **Risk:** Editing a named shim has no effect on the live site while middleware is in place. This can mislead contributors into thinking they have edited the active handler.

## Production Worker Architecture

### Confirmed from repo

- `scripts/build-standalone-worker.mjs` reads all files from `public/` and the routing/API functions, and generates a single self-contained Worker `.js` file.
- The generated Worker embeds static assets as base64 or gzip-encoded strings rather than using `env.ASSETS.fetch()`.
- The generated Worker output path is `/tmp/tourticketcompare-worker.js` by default.

### Inferred from HANDOVER.md (requires Cloudflare dashboard verification)

- Production custom domains (`tourticketcompare.com`, `www.tourticketcompare.com`) route to Worker `tourticketcompare-live`.
- Last known Worker deploy: 2026-05-01, build ID `d3cc71487403`.
- `www.tourticketcompare.com` redirects to the apex domain.

### Key implication

**`npm run deploy` and `npm run deploy:pages` both deploy to Cloudflare Pages, NOT to the production Worker.** Pages deploys do not update the live custom domains while Worker routes are active. To update production, the Worker must be rebuilt and deployed separately. See `docs/DEPLOYMENT.md`.

## Known Architectural Ambiguities

### 1. Worker vs Pages production ownership

Production traffic goes to Worker `tourticketcompare-live`. Pages serves a preview URL. There is no `npm run` command to deploy the Worker. The Worker source is not committed — it is generated from `scripts/build-standalone-worker.mjs`. This means:

- Code changes in `functions/` or `public/` must be followed by `node scripts/build-standalone-worker.mjs` and a manual Worker upload to take effect in production.
- A Pages deploy (`npm run deploy:pages`) updates the preview URL but NOT production.
- The repo does not contain the last deployed Worker binary. Rollback requires rebuilding from the last known-good commit.

**Requires verification:** Whether the Cloudflare routes still point to `tourticketcompare-live`, and whether the current `main` branch matches the deployed Worker.

### 2. Deployment path uncertainty

The Pages Functions source and the standalone Worker source share `[[path]].js`, but the Worker bundles static assets differently (inline) vs Pages (served from `env.ASSETS`). If `[[path]].js` uses `env.ASSETS.fetch()` in a way the Worker build script does not replicate, behaviour diverges between preview and production.

**Requires verification:** That the Worker build script correctly replicates `env.ASSETS` behaviour for all data files used by `[[path]].js` and `shows.js`.

### 3. Routing precedence risks

`_routes.json` routes `/*` through functions. This means:

- Any uncaught exception in a Pages Function returns a blank or error response rather than falling back to the static `public/` file.
- If `_middleware.js` throws, all HTML routes fail.
- Adding a new file to `functions/` with a matching route name could silently shadow or double-handle a route.

### 4. Named shim fragility

The named shims provide a safety net if middleware is removed, but are otherwise unused. A contributor editing `functions/artists.js` expecting to affect artist route behaviour would see no change while `_middleware.js` is active.

### 5. Vercel path

`vercel.json` and `api/` exist in the repo. These are not production but could be accidentally used as a deploy target. Do not add Vercel-specific logic unless a deliberate architecture decision is made.

### 6. Placeholder D1 bindings

`wrangler.toml` contains commented-out D1 bindings with `replace-with-d1-database-id` placeholders. Uncommenting them with placeholder values would break local Pages dev and any CLI deploys that read `wrangler.toml`.

## What Requires Manual Cloudflare Verification

Before trusting any production behaviour, verify in the Cloudflare dashboard:

- [ ] Custom domain routes still point to Worker `tourticketcompare-live` (not Pages)
- [ ] Worker `tourticketcompare-live` bindings: `DEMAND_DB`, `IMPACT_ACCOUNT_SID`, `IMPACT_AUTH_TOKEN`
- [ ] `MOCK_MODE` and `ALLOW_MOCK_PRICES` are `false` in the Worker environment
- [ ] `www.tourticketcompare.com` redirect is active at the Worker level
- [ ] Pages preview URL is separate from the custom domain routes
- [ ] No stale Route rules pointing to old Workers, Vercel, or Pages
